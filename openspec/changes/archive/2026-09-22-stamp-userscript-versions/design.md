## Context

Tampermonkey installs an update only when the version served from `@updateURL` compares greater
than the installed one. The repository commits its generated userscripts and has a verification
contract that rebuilding against unchanged data must produce byte-identical files. A stamp taken
from the wall clock on every build would satisfy the updater and break that contract, dirtying
two multi-megabyte files on every rebuild.

## Goals / Non-Goals

**Goals:**

- An installed userscript updates itself from `master` after a rebuild is pushed.
- The version moves whenever the generated bytes move, and never otherwise.
- The published URL is derived from the one place repository paths are declared.

**Non-Goals:**

- Hosting the userscripts anywhere other than the repository's raw GitHub URLs.
- A local development loop; that is a `@require file://` stub outside the repository.
- Changing browser behaviour, dictionary data, or the runtime.

## Decisions

1. **Compare the draft with the committed file, ignoring the stamp.** The builder renders the
   runtime with a pending placeholder version, normalizes the committed file's version to the
   same placeholder, and compares. Equal means the stamp is carried over; different means a new
   stamp. Hashing the data inputs instead was rejected because a runtime or builder edit also
   changes the output and must also raise the version.

2. **Stamp with the build date plus a counter.** `YYYY.MM.DD` stays readable and sorts
   correctly under Tampermonkey's numeric segment comparison. When the previous version is not
   older than today's date — a second change on the same day, or a clock that ran ahead — a
   trailing counter is incremented or appended, which guarantees a strictly greater version
   without depending on the clock being right.

3. **Derive the update URL from `scripts/lib/paths.js`.** The generated userscript filenames are
   already declared there; the raw base URL joins them. The runtime headers hold placeholders,
   so the branch and filenames are not spelled out a second time.

## Risks / Trade-offs

- **[The stamp lags a same-day push]** → The counter makes each same-day change strictly
  greater, so consecutive pushes on one day still update.
- **[A hand-edited `@version` in a runtime header would be silently overwritten]** → The header
  carries an explicit `__ZOOPDOG_VERSION__` placeholder, and `renderRuntime` fails loudly if it
  is missing.
- **[The update URL pins `master`]** → Recorded in the design and documentation; a copy
  installed from `master` keeps updating from `master`.
